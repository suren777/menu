# menu — agent conventions

Agent-facing conventions for the menu repo. Facts only — verify against the code before acting on them.

## What this repo is

Menu is a recipe **sourcing lab**: discovering recipe URLs, fetching pages politely, and extracting recipe data. It has no bot, no API and no deployment. Code that works here graduates to
[food-guru](https://github.com/surenislyaev/food-guru)'s `backend/app/ingest/` with minimal rework — so module layout, naming, tooling and code style deliberately mirror food-guru. When in doubt about how something should be implemented here, check how food-guru's ingest does it.

The boundary with food-guru: menu discovers, fetches and extracts **raw** structured recipe data (JSON-LD, or schema.org microdata when a site publishes no JSON-LD); parsing/structuring recipes into a real data model is food-guru's job. The ingredient structuring and nutrition prototype below is the one deliberate exception: a menu prototype that moves to food-guru with the ingest code. The Postgres 18 database (`docker compose up -d db`) is scratch storage for experiments, never the source of truth — still disposable, don't build anything on its schema (the ingredient, reference and nutrition tables included).

## Python 3.14

This repo runs on Python 3.14 (`requires-python = ">=3.14"`, migrated from 3.11 in Oct 2026). Assume newer-than-training-data syntax; read `pyproject.toml` before pinning anything.

## Commands

```sh
docker compose up -d db    # the scratch Postgres 18 server — the CLI needs it
uv sync                    # install/refresh dependencies
uv run pytest              # tests (need Docker: an ephemeral Postgres per run)
uv run mypy menu tests     # type check (strict)
uv run ruff check .        # lint (rule set matches food-guru's)
uv run black --check .     # formatting — CI runs this and isort too
uv run isort --check-only .
uv run pytest --cov=menu --cov-report=term-missing  # coverage, on demand
```

The compose volume mounts `/var/lib/postgresql` — the postgres:18 image moved `PGDATA` there from the pre-18 `/var/lib/postgresql/data` layout.

## Scraping rules

- **Politeness delay** — `fetch.py` spaces requests to a site's host by the site's `politeness_delay`. The delay lives in process memory (`_politeness`), so the crawl must stay **single-process**: parallel workers would each hammer the site at full speed. Same reason food-guru's worker is single-process.
- **Disk cache** — fetched pages are cached under `.cache/` (gitignored, safe to delete) and reused on re-runs; sitemaps are always fetched fresh but cached too, for replay. A failed fetch is never cached, so a transient error can't poison later runs.
- **`menu-rebuild` replays the cache offline** — it builds a fresh database (default `menu_rebuilt`, `--target` names another) on the same server as the live database from `.cache/`, the seeds and any downloaded reference releases with no network access; sitemaps or pages missing from the cache stay pending/queued for the next live crawl.
- **Test against saved pages** — don't write tests that hit live sites. Save the page HTML and test the parsing against the saved fixture.
- **Bad URLs don't stop the crawl** — every URL's outcome is recorded on its `pages` row (`failed`/`blocked`/`disallowed`, with the HTTP status and error), the crawl logs it, counts it and moves on; a sitemap that won't fetch is marked failed on its `sitemaps` row and the crawl moves on too. Mirrors food-guru's worker, which counts a failure and moves on. The same rule holds per ingredient line: `store_recipe_ingredients` stores a line that fails to parse with `parse_status='failed'` and moves on.
- **robots.txt is honoured** — `fetch.py` fetches each site's robots.txt once through the shared session and caches the parser (single process, like the politeness delay). A disallowed URL raises `DisallowedError` before anything is fetched; the robots crawl-delay joins the site's `politeness_delay`, whichever is larger. A 4xx (no robots.txt) allows all, a 5xx disallows all (RFC 9309).
- **Blocks stop the crawl** — 401/402/403 raise `BlockedError`, and a 429 is waited out once (honouring Retry-After) before it counts as a block too. Five consecutive blocked pages raise `CrawlBlockedError` and stop the run; blocked pages and sitemaps keep their status in the ledger, so the next run picks up exactly where this one stopped — a site shutting us out is not a dead link.
- **Access policy is not negotiable** — sites that demand browser UAs, bot challenges or payment (see `integration_list.md`) have made a deliberate access decision. No UA spoofing, no headless-browser challenge clearing, no paying through the wall; if a site matters, the route is a licence conversation, not code.
- **Reference data licences** — import a nutrient/portion source only when its licence allows commercial use without share-alike (no CC BY-NC, no ODbL, no paid APIs whose results can't be stored), and keep its citation: each import stamps a `food_source` row with version, licence and citation, and food-guru must print it wherever the values show. `nutrition_plan.md` lists the candidates and their checked terms.

## Ingredients prototype

Ingredient lines are parsed and normalised in menu: `menu/ingest/ingredients.py` wraps `ingredient-parser-nlp` behind a `ParsedLine` dataclass, and `menu/ingest/units.py` converts quantities to base units (mass → g, volume → ml, count → piece, plus named count units such as slice) with pint — never hand-written factors. Lines are stored in `recipe_ingredients` pointing at canonical `ingredient_terms` rows (concepts live in `ingredients`), written in the same transaction as their `recipes` row (which carries `servings`; the site is the `pages` row's), and `uv run menu-ingest bbc_good_food --reparse` re-parses stored recipes without re-fetching. Like everything here it lives on the scratch DB and graduates to food-guru with the rest of the ingest.

- **Canonicalisation is term-driven** — every parsed name becomes an `ingredient_terms` row (the term is its `canonical_name`), and a line points at its term instead of at the concept, so re-pointing a term re-resolves every line that uses it with **no reparse**. `ingredients.origin` is `seed` (curated) or `auto` (a parser name the heuristics let through). Singularisation uses inflect (`canonical_name`), with leave-alone rules for words ending in "us"/"ss" — the old strip-a-trailing-s rule produced junk like "asparagu".
- **`--re-resolve` is the everyday command after a seed change** — `uv run menu-ingest --re-resolve` re-seeds and re-applies the review heuristics to the terms in one transaction (no parser), recomputes grams for every line (a new density or confirmed reference changes grams without changing any ingredient), and prunes. `--reparse` is only for parser or unit changes.
- **A line's effective ingredient** = its term's concept, or NULL when the line carries the line-level review flag or its term is `review`/`not_food` — one rule, `repository.effective_ingredient_id` (with its SQL twin `effective_ingredient_predicates`), which every reader (aggregation, derivation, reports, metrics, review lists) goes through. Grams are computed from the stored line columns, so `--re-resolve` can re-run them from the DB.
- **Models only suggest** — `uv run menu-ingest --suggest [queue,audit,pair,food_ref] [--suggest-limit N] [--dry-run]` builds the review input sets (`review_inputs.py`; local embeddings pick neighbours and reference candidates), sends them to the LLM (`llm_review.py`, Fireworks, key in `FIREWORKS_API_KEY`) and appends pending entries to `menu/db/ingredients/suggestions.json`, skipping anything already in it. Nothing changes until you set an entry's `status` to `accepted` in a reviewed diff; seeding then applies it like a hand seed. Run `--dry-run` first: it prints item counts and a token estimate. Never run it inside a crawl.
- **Typography and site boilerplate fold before parsing** — `canonical_name` folds typographic quotes (’ ‘ → ', “ ” → ") and NBSP/narrow NBSP to plain spaces before anything else, so "confectioners’ sugar" and its ASCII spelling resolve to one term. `SiteConfig.ingredient_strip_patterns` regexes (King Arthur's `r"\bKing Arthur\s+"`) are removed from each line before the parser sees it, case-insensitively and compiled once per site; `raw_text` stays the verbatim line, and the brand-free parsed names are what the seed terms key on.
- **Seeding runs at startup** — `main()` seeds the ingredient data right after `initialise()`, before crawling or reparsing, so a fresh DB never parses unseeded. Seeding upserts terms: every `ALIASES` entry (overriding an existing auto/review term), a `seed.NOT_FOOD` list of equipment the parser calls an ingredient (terms with no concept, excluded from aggregation and nutrition), and a self-term for every seed concept. Accepted entries in `suggestions.json` seed exactly the same way — the `seed.aliases()` / `line_overrides()` / `not_food()` / `food_refs()` accessors merge them into the hand lists (hand seeds win conflicts) — and `--re-resolve` treats accepted alias/variant/not_food terms as curated so it never reverts them. A seeded term wins over the heuristics, and `seed.LINE_OVERRIDES` fixes lines the parser merges outright ("70g milk or dark chocolate roughly chopped (optional)" parses as name "milk"; override → milk chocolate). Pruning (`prune_orphan_ingredients`) deletes unused `auto` terms, then `auto` concepts nothing points at and no curated reference keeps — seed concepts survive.
- **The review queue is two-level** — names the parser likely mangled (`name_needs_review`: ≥5 words, or containing " and "/" or ") become terms with `ingredient_terms.resolution='review'` (no concept) instead of becoming canonical ingredients; that column *is* the term-level queue. The line-level flag `recipe_ingredients.needs_review` (`line_needs_review`) is about the line's raw text — "pink and yellow food colouring gels" needs both gels, so an "and" captured as an alternative still loses one from the shopping list — and is kept per line so it never taints the term for other lines; a seeded term clears it. A parse that raises is stored too, with `parse_status='failed'` and no term. `menu-ingest <site> --fdc-report` lists canonical ingredients sharing an fdc_id with no seed term between them — hand-seeding candidates, never an auto-merge.
- **Variants are recorded** — a term carries the variant ("whole", "warm") the line resolved through; `aggregate(..., keep_variants=True)` splits the list back out ("milk (whole)"). Range quantities buy the upper end ("2-3 onions" → 3).
- **Tests use the real lines** — `tests/ingest/fixtures/bbc_lines.json` holds the ingredient lines taken verbatim from the cached pages (double spaces, no commas); the parse edge-case table is hand-written examples.

- **Cross-dimension aggregation is opt-in** — volume→mass needs a `density` row and count→mass a `unit_weight` row in `ingredient_conversions`, seeded by hand (`seed.DENSITIES_G_PER_ML`, `UNIT_WEIGHTS_G`) or derived from the confirmed conversion reference's portions, which are all kept as `portion` rows (small, medium and large egg; cup; stick) and each line's `conversion_id` names the row its grams came from: FDC `food_portion` gram weights (SR Legacy, FNDDS) and CNF conversion factors give household measures (cup, tbsp, medium), from which density and unit weight follow. Precedence is seed > FDC > CNF (`seed.CONVERSION_SOURCES`). Without them, lines stay separate ("250 ml + 100 g").
- **Reference data and derived nutrition** — `uv run menu-fdc-import` / `menu-cofid-import` / `menu-cnf-import` load each source's bulk release (downloaded once into `.cache/sources/<source>/`, never at ingest time; tests use small fixture slices) into the common `ref_*` tables. Ingredients map to reference foods through `ingredient_food_refs`, whose explicit `status` (candidate | confirmed | rejected) replaces the old role-NULL + boolean encoding: confirmed rows (hand-seeded in `seed.FOOD_REFS`, role conversion | nutrition) feed grams and nutrition — the database itself enforces one confirmed reference per role per source per ingredient — candidate rows are the parser's fdc_id suggestions that `menu-ingest --ref-review` lists for review, and a human rejection is recorded as a `food_ref` entry with `status: "rejected"` in `suggestions.json` (input `"food_ref"`, `evidence: {"reason": ...}`, `model: {"llm": "human"}`), which replaces the old `seed.REJECTED_REFS` list and keeps the rejection out of the report for good. `--derive-nutrition` takes each line's nutrients from the first confirmed reference in the site's `nutrition_sources` order; every value keeps its nutrient definition (CoFID's available carbohydrate is not FDC's by-difference), and a result that mixes definitions is flagged. Published nutrition is validation only (`--validate-nutrition`, `--coverage-report`).

## Adding a site

Adding a site is mostly config: add a frozen `SiteConfig` entry in `menu/ingest/sites/` and register it. Site-specific behaviour belongs there or in the site's module — the generic pipeline modules (`discover.py`, `fetch.py`, `extract.py`, `pipeline.py`) stay site-agnostic. `sitemap_urls` takes several sitemap indexes; `import_sitemap` detects a plain urlset and stores the sitemap URL itself as the single row.
